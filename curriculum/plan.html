    Toolchain

    note▶

    Quarto. A book-and-website generator built on Pandoc. One project renders an HTML site with sidebar navigation and search, plus PDF and EPUB, from plain .qmd files that are Markdown with a YAML header.

    Why it wins here

    • Lessons are Markdown, editable in any editor while sitting at Sonic Pi.
    • format: html, pdf, and epub in one config. quarto render produces all three.
    • Callouts, cross-references, footnotes, and an index are built in, so the print book gets real book features without hand-rolling them.
    • Lua filters allow one custom addition, an audio player next to code blocks, without forking anything.
    • No computation engine needed. Sonic Pi code is displayed, not executed, so there is no Jupyter or Knitr dependency and rendering stays fast.

    Rejected alternatives. mdBook makes a good site and a poor PDF. Jupyter Book is heavier and aimed at executable Python. Astro Starlight makes an excellent site and has no book path. Plain Pandoc plus a Makefile is what Quarto already is, minus the navigation and search.

    Prerequisites on this machine

    Already present: pandoc 3.10, ffmpeg 8.1, git, gh, Quarto 1.10.18, TinyTeX, qrencode, and Sonic Pi 5.0.0.

    • git init and create the GitHub repo. Nothing else works until this exists.
    • brew install --cask quarto
    • quarto install tinytex for PDF output. Around 100 MB, self-contained.
    • brew install qrencode for audio QR codes in the print book.

    Ruby 2.6 is on the system. Sonic Pi ships its own Ruby, so the system version only affects helper scripts. Those are POSIX shell and Python 3, so the question never comes up.

    Lesson file format

    note▶

    Every lesson uses the same skeleton. Consistency is what lets a reader skim.

    ---
title: "7. The envelope is the instrument"
subtitle: "25 minutes"
part: "Why sound has structure"
concepts: [envelope, attack, release, articulation]
sonic-pi: [play, use_synth, attack:, release:]
status: draft        # draft | tested | final
---

## The idea

Two or three paragraphs. What the musical concept is and what it does to
sound. No history unless the history explains the sound.

## Run this

```{.ruby audio="L07-1.mp3"}
# Same pitch, same synth, four envelopes.
...
```

What you just heard, in a sentence or two.

## Change one thing

Two or three directed experiments. Each states what to change and what to
listen for. The reader edits and runs. Nobody wants a transcript of
someone else editing and running.

## Why it works

The explanation, now that the sound is in your ears.

## Take it further

One optional harder exercise. No solution given.

## Ear drill

Present only in lessons that add a drill to drills.rb.

    The status field drives a build-time badge on the site, so readers know which lessons have been tested and which are fresh.

    Conventions

    • Code blocks are ruby for highlighting. Sonic Pi is Ruby with a DSL on top.
    • Every example that produces sound gets an audio= attribute. No exceptions.
    • Anything using randomness starts with use_random_seed 42 so the printed output, the recorded audio, and the reader's run all agree.
    • Comments in code carry the teaching. If a comment only restates the line, cut it.
    • Ruby idioms get a callout the first time and never again. Three sentences maximum. Blocks, symbols, ranges, each versus map, keyword arguments, and rings are the whole list.

    Audio on the website

    note▶

    A music book whose examples are silent is a reference manual. Every runnable example gets a recording next to it.

    Primary workflow, manual and reliable

    1. Paste the snippet into Sonic Pi, press Rec, press Run, press Rec again.
    2. Save as L07-1.wav into assets/audio/.
    3. scripts/make-audio.sh converts to mp3, trims leading silence, and normalises loudness so no example is twice as loud as its neighbour.
    ffmpeg -i "$1.wav" \
       -af "silenceremove=1:0:-50dB,loudnorm=I=-16:TP=-1.5" \
       -codec:a libmp3lame -q:a 4 "$1.mp3"

    The Lua filter

    It turns this:

    ```{.ruby audio="L07-1.mp3"}
play :c4
```

    into a highlighted code block followed by an <audio controls> element in HTML, and into a code block followed by a QR code and short URL in PDF. One filters/audio.lua, roughly forty lines, checks quarto.doc.is_format("html") and branches.

    Possible automation, to evaluate in Phase 2. Sonic Pi exposes an OSC interface that sonic-pi-tool can drive to evaluate a file and trigger a recording, which would let make-audio.sh regenerate every clip unattended. The port and authentication token changed between Sonic Pi 3 and 4 and are written into ~/.sonic-pi/log/.

    Treat this as an optimisation. If it takes more than an afternoon, keep pressing Rec by hand. There are fewer than 150 clips and each takes under a minute.

    Keeping the code correct

    note▶

    Snippets that do not run are the fastest way to lose a reader.

    • scripts/extract-code.sh walks every .qmd, pulls each fenced ruby block, and writes it to code/L07/01.rb with a header comment naming its source file and line. Pure text processing, no Quarto involvement.
    • scripts/check-code.sh runs each extracted file. Two tiers: ruby -c catches syntax errors and needs nothing installed, and evaluation through sonic-pi-tool catches undefined methods and bad arguments but needs Sonic Pi running. Tier one goes in CI. Tier two runs locally before a release.
    • Long examples get a # ...continued from above marker so extraction can join them into one runnable file.

    The point is not test coverage. The point is that after you rewrite a lesson in week nine, you find out the same day that it broke a snippet from week three.

format:

    theme: [cosmo, assets/theme/custom.scss]

    toc-depth: 2
  pdf:

    Deployment on push to main

    - uses: quarto-dev/quarto-actions/setup@v2
- run: quarto render --to html
- uses: peaceiris/actions-gh-pages@v4
  with:
    github_token: ${{ secrets.GITHUB_TOKEN }}
    publish_dir: ./_book

    PDF and EPUB are built locally and attached to a tagged release rather than on every push, because TinyTeX in CI is slow and the print book only needs regenerating when you decide it does.

    Domain. GitHub Pages gives gauden.github.io/coding-harmony. A custom domain via CNAME is a five-minute change whenever you want it.

    Writing standard

    note▶

    STYLE.md lives in the repo root, where it is visible to everyone writing, human or otherwise. It now opens with the voice rule: first person plural, bare imperatives for instructions, never "let's".

    • Zinsser's rule first: cut every word that carries no weight. Write the sentence, then remove a quarter of it.
    • Vary sentence length. A short sentence after two long ones is the only punctuation trick that always works.
    • No "not X, but Y". No rhetorical triplets unless the third item is genuinely needed. No em dashes where a full stop or a comma does the job.
    • Banned vocabulary: delve, matters, crucial, journey, unlock, harness (as verb), leverage (as verb), robust, seamless, powerful, elegant (as praise), simply, just, of course, obviously.
    • No encouragement. The reader is an adult who chose to be here. Do not tell them something is exciting; write it so that it is.
    • First person for the writer, second for the reader. The book says "I" because it is a record of one person learning. "We" is reserved for programmers as a group. Bare imperatives for direct instructions. Second person only for what belongs to the reader: their ear, their code, their judgement.
    • Musical terms in italics at first use, then plain. Define on first use in the sentence itself, not in a parenthesis.
    • Prefer the concrete instance to the general claim. "Play 220 Hz against 330 Hz" beats "consider a perfect fifth".
    • Read every lesson aloud before marking it tested. Anything you stumble over gets rewritten.

    Add scripts/lint-prose.sh that greps for the banned words and reports file and line. Cheap, and it catches drift.

    The drafting loop

    note▶

    I am the first student, and that is the main advantage this book has.

    For each lesson:

    1. Draft from the syllabus entry. Aim for a rough version, not a good one.
    2. Sit at Sonic Pi and do the lesson as written, from a cold start. Time it.
    3. Write field notes immediately in notes/field-notes.md: what confused you, what took longer than the stated duration, what you wanted to try that the lesson did not offer, what sounded worse than promised.
    4. Rewrite from the notes. This is where the book actually gets written.
    5. Record the audio, set status: tested, commit.

    Keep field notes even when a lesson goes well. "This took 12 minutes not 25" is as useful as a complaint.

    Two rules that keep the loop honest. Never fix a lesson while doing it, because the confusion is the data. Never draft more than four lessons ahead of what you have tested, because the untested part builds on assumptions the testing would have disproved.

    Decisions

    note▶

    All four are settled. The reasoning is kept here because a decision without its reason gets reopened.

    Licence settled

    Dual licence, following Allen Downey's arrangement for Think Python. Code under MIT, text under CC BY-NC-SA 4.0. Recorded in LICENSE.md at the repo root.

    • Code, meaning Sonic Pi examples, scripts, filters, and build config: MIT. A reader can lift any snippet into work they sell.
    • Text, meaning lesson prose, curriculum, diagrams, and audio: CC BY-NC-SA 4.0. Share and adapt non-commercially, with attribution, under the same terms.

    The non-commercial term binds others, not the copyright holder. Selling the book stays open to us.

    Notation diagrams settled

    LilyPond to SVG. Correct notation, regenerable from source, consistent across every diagram in the book. The cost is that LilyPond is fiddly and adds a build dependency.

    Needed from Part 8 onwards. Install with brew install lilypond when Phase 3 starts; nothing before then requires it.

    Interactive site examples settled

    Copy button plus audio player. Quarto's code-copy gives every block a copy control, and filters/audio.lua attaches a recording beneath it. The reader copies, pastes into Sonic Pi, and runs.

    A browser-based Sonic Pi does not exist, so this is the ceiling until something changes.

    Solutions to exercises settled

    Full solutions appendix. Every Take it further exercise gets a worked answer in appendix/solutions.qmd, generated with one section per lesson.

    The reader is working alone with no one to ask. A withheld answer stops being a teaching device and becomes a dead end.

    What could go wrong

    note▶

    The project stops halfway. This is the most likely way the book fails, and it has nothing to do with music or code. Around Lesson 20 the novelty has worn off, the remaining work is visible, and the finish line is still months away. Most self-taught book projects die at roughly that point.

    What helps, concretely:

    • Publish from day one. Done. The site deploys on every push, so whatever exists is already public and already useful to someone. A book abandoned at Lesson 25 is still a 25-lesson course online, which is a real thing rather than a failure.
    • Never break the chain on the ear drills. Ten minutes counts. The drills are the habit that keeps the project present on days with no writing in them.
    • Stop mid-lesson, not at the end of one. Leaving a half-finished paragraph makes the next session trivial to start. A clean stopping point is the hardest thing to return to.
    • Take the fourth week off from theory. It is in the working rhythm for this reason. Transcribing something you actually want to hear is the reward that makes the next three weeks happen.
    • Let the lesson count move. 58 is a plan, not a debt. Merging two lessons or cutting one is progress. Treating the number as fixed turns a flexible project into an obligation.
    • Watch for the tell. Two weeks without a commit is the signal. Not a reason to feel bad, a reason to check whether the next lesson is badly scoped and needs splitting.

    Audio recording becomes a chore. 150 clips at a minute each is two and a half hours spread over months, which is fine. It stops being fine when a rewrite invalidates recordings you already made. Mitigation, agreed: record nothing until the lesson reaches status: tested. This is now written into STYLE.md as well, so it survives being forgotten.

    Snippet rot. A Sonic Pi release changes a default and forty examples sound different. Mitigation, done: setup.qmd pins Sonic Pi 5.0.0, the version on this machine, and tells the reader how to check theirs. Run scripts/check-code.sh --deep before each release, and whenever the pin moves.

    Writing drifts into tutorial voice. The temptation to encourage is strong when writing for beginners. Mitigation: STYLE.md, the prose linter, and reading aloud.
